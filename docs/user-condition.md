# 사용자 조건 직접 입력

## 범위와 흐름

웹과 Android의 단어 조합 화면에 선택 입력창을 추가한다. 새 주제 선택 시 빈 값으로 시작하며 단어 리롤, 내 단어 적용, 화면 이동에서 현재 입력값을 유지한다. 무작위 기본 조건을 자동으로 채우지 않는다.

- 최대 100자, 입력 중 현재 글자 수/100 표시. 웹 maxlength와 Android LengthFilter에 맞춰 UTF-16 코드 단위로 계산하므로 이모지는 두 칸 이상을 사용할 수 있다.
- 빈 값과 공백만 있는 값으로도 생성할 수 있다. 요청 직전 바깥 공백은 제거한다.
- 결과 및 구체화 화면에 해당 결과를 생성할 때 사용한 조건을 표시한다. 비어 있으면 ‘입력한 조건 없음’으로 표시한다.
- 조건은 현재 세션과 초안에 보관한다. 웹 localStorage, Android 앱 전용 JSON 초안에 포함되며 명시적으로 저장한 아이디어 및 TXT 내보내기에도 포함된다. 새 주제는 이전 조건을 자동으로 이어받지 않는다.
- 생성·다듬기·구체화 요청에 `condition`을 JSON 문자열로 전달한다. 예: `{"condition":"1인 가구를 위한 서비스"}`. 빈 값은 `{"condition":""}`.
- 규칙 시연은 조건을 기록·표시할 뿐 제약을 추론하지 않는다. AI에 제약을 전달했다는 사실도 실제 예산·안전성·사용성을 만족했다는 보장이 아니다.

## 검증 정책

명시적인 욕설·금지 주제 목록은 제공되지 않았으므로 임의 키워드 차단을 도입하지 않았다. 현재 ‘금지된 입력’은 형식상 부적절한 문자로 한정한다.

1. 문자열 여부, 최대 100자 검사. 자르거나 다른 조건으로 자동 대체하지 않고 오류로 거절한다. UI의 최대 길이 제한은 직접 입력을 100자로 제한한다.
2. C0/C1 제어문자, 줄바꿈·탭, 양방향 표시 제어문자, 잘못된 단독 UTF-16 서로게이트를 차단한다. 정상 한국어·숫자·기호·이모지는 허용한다.
3. 웹 입력 컴포넌트와 `runGeneration` 진입점에서 검사한다. OpenAI/Gemini/WebLLM은 공통 `buildMessages`에서 다시 검사하므로 UI를 건너뛴 호출도 요청 전에 거절한다. 규칙 생성도 검사한다.
4. Android UI, AppSession, AiEngine, DemoDomain 진입점에 대응 검사를 적용한다.
5. 조건을 HTML로 실행하지 않고 React 텍스트와 Android TextView로 표시한다. 프롬프트에서는 조건을 사용자 제약 데이터로 구분하며 시스템·출력 형식을 덮어쓰는 명령으로 취급하지 않는다. 이 조치만으로 모든 프롬프트 공격이나 유해 콘텐츠를 차단한다고 주장하지 않는다.

## 서버 검증: 합의된 구현 범위에서 제외

교수님 지침에 따라 자체 API 서버·DB는 구현 범위에서 제외했다. 이에 종속된 자체 서버 검증도 이번 범위 밖이며 미완성 과제로 분류하지 않는다. Render Static Site는 정적 파일을 제공하므로 서버 요청 본문을 검사하는 실행 지점도 없다. 클라이언트의 AI 요청 직전 재검사는 서버 검증이 아니며 클라이언트 변조를 방어하는 서버 신뢰 경계를 대체하지 못한다.

서버를 향후 추가한다면 인증·요청 크기 제한과 함께 수신한 원본 `condition`의 타입·길이·제어문자를 독립적으로 검증하고, 유효하지 않은 요청은 HTTP 400으로 거절한 후에만 모델에 전달해야 한다. 웹의 순수 함수 `validateCondition`은 Node 서버에서도 재사용할 수 있지만 지금 서버 라우트를 배포했다는 뜻은 아니다. 제공업체의 안전 필터도 이 제품의 서버 검증 구현을 대신하지 않는다.

## 검증

- 자동 테스트 78개: 빈 값/100자/101자/제어문자/양방향 제어/유니코드, 각 AI 요청 JSON과 요청 전 거절, 세션·저장·TXT 유지, 웹·Android 연결 지점 포함.
- 웹 브라우저에서 빈 값 생성, 100/100 표시, 제어문자 시 오류·버튼 비활성화, 리롤 후 유지, 새로고침 후 이어보기, 결과 조건 표시, 저장, 새 세션 빈 값 초기화를 확인했다.
- 외부 모델은 모의 전송 검사이며 개인 키로 비용이 발생하는 실제 추론·제약 준수 품질을 검증한 것은 아니다.
- 웹 빌드·Android APK 빌드 및 설치 성공. 에뮬레이터는 초기 검증 중 연결 정지가 있어 스냅샷을 불러오지 않는 새 부팅으로 재시도했다. 최종 Android 코어 검증 18개 그룹 통과: 조건 검증 및 네이티브 입력·카운터·리롤·초안·결과 표시 포함. 기존 보관함 파일은 검증 전후 SHA-256이 같았다.
- 실제 휴대폰의 키보드·터치·세이프 영역은 실기기 확인이 필요하다. 데스크톱 브라우저·에뮬레이터 검증을 실기기 테스트라고 부르지 않는다.
